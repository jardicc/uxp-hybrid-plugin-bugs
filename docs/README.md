# UXP Hybrid Plugin SDK — Code Audit Summary

This directory contains a complete code audit of [`src/`](../src), [`template/`](../template), and the original SDK `README.md` (commit `dc21035`), with one Markdown file per bug detailing the affected files, problematic code, root cause, reproduction steps, and suggested fix.

## SDK Core vs. Template / Sample Plugin Breakdown

A critical distinction when auditing or using this repository is separating bugs in the **reusable SDK Core (`src/api/` and `src/utilities/`)** from bugs that exist **only in the provided sample/template plugin (`template/template-dev/`, `template/template-plugin/`, and `README.md`)**:

### 1. SDK Core Bugs (`src/api/` & `src/utilities/` — 15 Bugs)
These bugs live in the SDK's C/C++ ABI headers (`src/api/`) or C++ helper classes (`src/utilities/UxpValue.*`, `UxpTask.*`, `UxpAddon.*`, which are also copied into `template/template-dev/src/utilities/`). **Any third-party UXP hybrid plugin that links or includes these SDK files inherits these bugs:**
- **C++ `Value` Wrapper (`src/utilities/UxpValue.h`, `src/utilities/UxpValue.cpp`) — 7 Bugs:**
  - **#01**: JS `Array` is misclassified as `Value::Kind::map` because `case addon_object:` runs before `uxp_addon_is_array()`, turning arrays into plain `{ "0": ... }` objects.
  - **#03**: `Value(Value&&)` move constructor zeroes `data.* = nullptr` without resetting `kind = Kind::undefined`, causing null-pointer dereferences if a moved-from `Value` is inspected.
  - **#04**: `class Value` defines a custom destructor and move constructor without move-assignment (`operator=`) or copy operations.
  - **#05**: `Value(addon_env, addon_value)` allocates `new ListType` / `new MapType` with raw `new` and leaks the entire C++ heap container whenever a nested element throws (and recurses infinitely on cyclic objects).
  - **#06**: `addon_null` (`null`) is unhandled in `GetType()`, throwing `"unsupported type"` on `null` or any JSON object containing a `null` property.
  - **#07**: `GetMap()` enumerates the prototype chain (`kIncludePrototypes` — failing on inherited prototype methods), silently drops colliding `\0`-truncated keys in `std::map::emplace`, reorders keys alphabetically, and omits `uxp_addon_coerce_to_string`.
  - **#08**: `GetString()` uses `std::string(&buffer[0])` instead of `actualLength`, silently truncating strings at the first embedded `\0` byte.
- **C++ Addon Error & Lifecycle Helpers (`src/utilities/UxpAddon.h`, `src/utilities/UxpAddon.cpp`) — 2 Bugs:**
  - **#09**: `Check()` and `UxpValue` throw raw `const char*` string literals, whereas `UXP_ADDON_INIT`, `UXP_ADDON_TERMINATE`, and `CreateErrorFromException` only catch `const std::exception&` (erasing all error messages to `"unknown exception"` or crashing across `extern "C"`).
  - **#10** *(SDK Core + Template Addon)*: `CreateErrorFromException()` calls `uxp_addon_create_error` and returns the `Error` object as a normal return value instead of throwing a JS exception (`uxp_addon_throw_error`), fails to check `uxp_addon_is_exception_pending` when a JS getter throws, and calls `std::terminate()` if no exception is active.
- **C++ Async `Task` Scheduler (`src/utilities/UxpTask.h`, `src/utilities/UxpTask.cpp`) — 2 Bugs:**
  - **#11** *(SDK Core + Template Addon)*: Empty `catch (...) {}` blocks in `Task` thunks and `module.cpp` swallow exceptions without calling `uxp_addon_reject_deferred`, leaving JS Promises pending forever.
  - **#12**: `Task` single-use guard checks `mDeferred != nullptr` (which is reset to `nullptr`), omits null checks on `mEnv`, and accesses `Task` state across threads without synchronization.
- **C/C++ ABI Headers (`src/api/UxpAddonShared.h`, `src/api/UxpAddonTypes.h`) — 4 Bugs:**
  - **#13**: Missing `#define` keyword in `#else` branch of `UXP_EXTERN_API_STDCALL(type)`.
  - **#14**: `uxp_addon_terminate_func` has wrong return type (`addon_value` instead of `void`) and omits `UXP_EXTERN_API_STDCALL`.
  - **#15**: Inconsistent `#pragma pack` alignment between `UxpAddonTypes.h` (16-byte) and `UxpAddonShared.h` (8-byte on x86/ARM64).
  - **#16**: C++-only rvalue reference `addon_apis&&` inside `extern "C"` entry point declarations and C++11 typed enums in C/C++ shared headers.

### 2. Template / Sample Plugin Only Bugs (`template/` — 5 Bugs)
These bugs exist **only in the sample template (`template/template-dev/` and `template/template-plugin/`)**, not in the core SDK (`src/`). A developer writing their own JS plugin and C++ entrypoints from scratch will not hit them unless they copy-paste code from `template/`:
- **Sample JavaScript Plugin (`template/template-plugin/main.js`, `template/template-dev/src/main.js`) — 2 Bugs:**
  - **#02**: `testMyAsyncEcho()` wraps `addon.my_echo_async(10)` in an unawaited `new Promise(...)` and calls `resolve(result)` synchronously where `result` is an undeclared identifier (`ReferenceError: result is not defined`).
  - **#19**: `messageDialog()` calls `document.appendChild(dialog)` instead of `document.body.appendChild(dialog)`, sets unitless `fontSize = 20`, provides no close button, and leaks `<dialog>` nodes in the DOM.
- **Sample C++ Addon Entrypoints (`template/template-dev/src/module.cpp`) — 2 Bugs:**
  - **#17**: `MyEcho()` and `MyAsyncEcho()` declare `addon_value arg1;` uninitialized on the stack and never check `if (argc < 1)` after `uxp_addon_get_cb_info`.
  - **#18**: `Init()` continues executing after `uxp_addon_throw_error`, reuses a non-zeroed `fn` pointer across registrations, and overwrites pending exceptions.
- **Sample Visual Studio Project (`template/template-dev/win/Sample-Uxp-Addon.vcxproj`) — 1 Bug:**
  - **#20**: `AdditionalIncludeDirectories` uses `..\..\..\..\src\api` (4 parent levels instead of 3), `Release|x64` is misconfigured, and `template/template-dev/src/utilities/` contains an out-of-sync copy of `src/utilities/`.

### 3. SDK Documentation Only (`README.md` — 1 Bug)
- **#21**: Root `README.md` omits `await` on `require("sample-uxp-addon.uxpaddon")` (causing `TypeError: addon.my_function is not a function`), swaps `addon_deferred` and `addon_value` types in `uxp_addon_create_promise`, has C++ syntax errors, and contradicts `module.cpp` regarding the `Init` thread.
